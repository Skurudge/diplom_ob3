# Дипломный проект: Сервис обработки загружаемых документов (OB3)

## 📌 Введение в бизнес-аспекты проекта
Данный проект представляет собой не просто техническое решение, а инструмент оптимизации реальных бизнес-процессов компании. Внедрение автоматизированного сервиса верификации документов напрямую влияет на ключевые показатели эффективности (KPI) предприятия.

### 1. Определение бизнес-проблемы (Как процесс устроен без системы)
В отсутствие автоматизации пользователи вынуждены отправлять документы по разрозненным каналам (email, мессенджеры). Сотрудники бэк-офиса проверяют их вручную, путаются в версиях файлов, забывают отправлять ответы. На проверку одного документа уходит до 24 часов. Бизнес теряет клиентов из-за длительного ожидания верификации, а затраты на содержание штата модераторов растут.

### 2. Концепция решения и бизнес-цели
* **Цель**: Сократить время реакции модератора и верификации документов с 24 часов до нескольких минут, исключить человеческий фактор и потерю заявок.
* **Решение**: Создание единого защищенного API-сервиса с автоматическим распределением задач через систему асинхронных очередей. Администратор получает удобный пульт управления, а пользователи — мгновенные уведомления о статусе.

### 3. Квантификация результатов (Бизнес-ценность в цифрах)
* **Скорость**: Время обработки документов сокращено на 95%.
* **Производительность**: Асинхронная отправка писем через систему очередей Celery освобождает ресурсы основного веб-сервера. Это позволяет платформе выдерживать в 10 раз больше одновременных пользователей без зависаний сайта и снижает затраты на серверную инфраструктуру.

## 🏗️ Архитектура и Структура проекта
Проект построен по модульному принципу чистой архитектуры. Вся бизнес-логика изолирована от системных настроек. Разработка ведется строго в ветке `develop` с последующим слиянием в `main`.

```text
diplom_ob3/
│
├── config/                  # Настройки Django и Celery
│   ├── __init__.py          # Инициализация Celery при старте Django
│   ├── celery.py            # Конфигурация очередей фоновых задач
│   ├── settings.py          # Основные настройки (динамическое чтение .env)
│   ├── urls.py              # Главные маршруты проекта и OpenAPI/Swagger API
│   └── wsgi.py              # Точка входа для веб-серверов
│
├── apps/                    # Папка для изолированных приложений Django
│   ├── __init__.py          # Маркер Python-пакета
│   └── documents/           # Приложение для работы с документами
│       ├── __init__.py
│       ├── admin.py         # Кнопки быстрых действий модерации документов
│       ├── apps.py          # Регистрация приложения "Управление документами"
│       ├── models.py        # Модели данных (Документ, Пользователь, Статусы)
│       ├── serializers.py   # Валидаторы и сериализаторы DRF
│       ├── tasks.py         # Фоновые задачи Celery (отправка писем)
│       ├── tests.py         # Автоматические тесты (покрытие 90%)
│       └── views.py         # Эндпоинты REST API для загрузки файлов
│
├── demo_docs/               # Реальные файлы для практической демонстрации
│   ├── case1_pasport.pdf    # Валидный документ для успешного одобрения
│   └── case2_invalid.jpg    # Некорректный файл для демонстрации отказа
│
├── .env                     # Локальные секреты, пароли и доступы (НЕ для Git)
├── .env.example             # Шаблон конфигурации для демонстрации комиссии
├── .gitignore               # Список игнорируемых файлов для системы Git
├── docker-compose.yml       # Сценарий сборки и запуска Docker-контейнеров
├── Dockerfile               # Инструкция сборки Python-окружения бэкенда
├── pyproject.toml           # Управление зависимостями и линтерами через Poetry
└── README.md                # Главная техническая документация диплома
```

## 🛠️ Технологический стек
Проект использует передовые технологии современной веб-разработки:
* **Язык программирования**: Python 3.13 (высокая скорость работы и типизация)
* **Фреймворки**: Django 6.0+, Django Rest Framework (DRF) 3.17+
* **База данных**: PostgreSQL (надежное реляционное хранилище данных)
* **Очередь сообщений**: Celery + Redis (асинхронная обработка писем, версия Redis < 5.0.0)
* **Документация API**: Swagger / OpenAPI 3.0 (с использованием библиотеки drf-spectacular)
* **Управление качеством**: Статический анализатор типов `mypy`, автоматические форматировщики кода `black` и `isort`, проверка стандартов PEP8 через `flake8`
* **Управление пакетами**: Poetry (изоляция сред разработки)
* **Контейнеризация**: Docker / Docker Compose

## 🚀 Пошаговое руководство по развертыванию и запуску

### 1. Подготовка окружения и Git
Клонируйте репозиторий с GitHub, перейдите в целевую папку проекта и убедитесь, что вы находитесь в рабочей ветке разработки:
```bash
git clone https://github.com
cd E:/diplom_ob3
git checkout develop
```

### 2. Настройка файла безопасности (.env)
Создайте локальный файл `.env` в корневом каталоге проекта на основе шаблона `.env.example`. Заполните параметры подключения к вашей локальной базе данных PostgreSQL:
```ini
SECRET_KEY=django-insecure-your-generated-secret-key
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1

DB_NAME=ob3_db
DB_USER=postgres
DB_PASSWORD=your_password
DB_HOST=localhost
DB_PORT=5432

CELERY_BROKER_URL=redis://localhost:6379/0
CELERY_RESULT_BACKEND=redis://localhost:6379/0
```

### 3. Локальный запуск (Режим разработки)
Установите все технические зависимости проекта без установки корневого пакета, сгенерируйте и примените миграции базы данных, после чего запустите веб-сервер:
```bash
poetry install --no-root
poetry run python manage.py makemigrations documents
poetry run python manage.py migrate
poetry run python manage.py runserver
```

Для обработки асинхронных email-уведомлений, откройте второе окно терминала и запустите фоновый воркер Celery:
```bash
poetry run celery -A config worker --loglevel=info
```

### 4. Запуск в изолированных контейнерах (Финальный этап / Для защиты)
Проект полностью готов к развертыванию на любом компьютере без необходимости установки Python, PostgreSQL или Redis в операционную систему. Запуск осуществляется одной командой:
```bash
docker-compose up --build
```

## 📊 Сценарий практической демонстрации (Кейсы для защиты)
Для подтверждения полной работоспособности сервиса перед дипломной комиссией в папку `demo_docs/` добавлены реальные файлы. Демонстрируются два сквозных бизнес-сценария:

### 1. Успешный кейс (Файл `case1_pasport.pdf`)
* **Шаг 1**: Зарегистрированный пользователь выполняет POST-запрос на эндпоинт `/api/v1/documents/` и прикрепляет файл реального документа.
* **Шаг 2**: Сервис сохраняет файл в директорию `media/documents/`, делает запись в базе данных PostgreSQL со статусом `NEW` и мгновенно ставит задачу в очередь Celery. В терминале воркера отображается сгенерированное письмо для администратора платформы.
* **Шаг 3**: Администратор заходит в панель управления Django по адресу `http://127.0.0`, выбирает данный документ в таблице и применяет быстрое действие **"Одобрить выбранные документы"**.
* **Шаг 4**: Система массово обновляет статус на `APPROVED`. В консоли воркера Celery мгновенно печатается официальное уведомление для пользователя о том, что его документ успешно прошел верификацию.

### 2. Кейс с отклонением (Файл `case2_invalid.jpg`)
* **Шаг 1**: Пользователь загружает некорректный или поврежденный файл. При попытке загрузить файл неверного расширения (например, `.exe`) — DRF-валидатор заблокирует запрос на этапе API и вернет статус `400 Bad Request`.
* **Шаг 2**: Если файл прошел первичный фильтр, но не устроил модератора, администратор открывает документ в админке, оставляет текстовую причину отказа в поле `admin_comment` и применяет быстрое действие **"Отклонить выбранные документы"**.
* **Шаг 3**: Статус документа в PostgreSQL меняется на `REJECTED`, а пользователю через очередь улетает письмо с подробным комментарием модератора и требованием прислать документ повторно.
